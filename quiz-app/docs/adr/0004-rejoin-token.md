# ADR 0004: 切断は退室とせず、再参加はホストが渡すトークンで本人を確かめる

- ステータス: 承認
- 日付: 2026-10-11
- 関連: [#20](https://github.com/shared-yung/quiz-match/issues/20) / [P2P メッセージプロトコル](../spec/p2p-protocol.md) / [ゲームルール](../spec/game-rules.md) / [ADR 0001 通信方式](0001-transport.md)

## 背景

WebRTC の接続は、回線の瞬断やタブの裏回しでも切れる。切れるたびにプレイヤーがゲームから外れ、得点を失うのでは遊べない。

一方で、接続を張り直すと `PeerId` は変わる。手動シグナリング（[ADR 0003](0003-signaling.md)）では、ホストが招待し直した**新しい接続**でつながり直すしかない。ホストから見ると、知らない接続から誰かが来たのと区別がつかない。**同じプレイヤーだと確かめる手段が要る。**

ホストの切断はもっと深刻で、状態の正本がホストのメモリにしか無い（[ADR 0001](0001-transport.md)）。

## 検討した選択肢

再参加した人の本人確認について。

1. **参加を受け付けたときにホストがトークンを渡し、再参加ではそれを名乗らせる**（採用）
2. 表示名で照合し、切断中の同名プレイヤーに結び直す
3. 再参加を区別せず、新規の参加として扱う（得点は 0 から）

## 決定

**選択肢 1 を採用する。** あわせて次を決める。

- **切断は退室ではない。** 切断したプレイヤーはルームに残り、得点も枠も保たれる。参加者一覧では「切断中」として扱う
- ホストは参加を受け付けたら `join/accepted` で、本人にだけ id とトークンを送る。プレイヤーは張り直した接続で `rejoin` を送り、トークンを名乗る
- 覚えの無いトークン、または退室済みのプレイヤーのトークンは `join/rejected`（`unknownToken`）で断る
- 再参加と途中参加の人には、`room/state` と、出題中なら公開済みの文字を送り直す（途中経過）
- **ホストの切断からは復帰しない。** ホストの状態は永続化しない。プレイヤーには「ホストとの接続が切れた」と表示し、再招待を待つ。ホストが生きていれば同じプレイヤーで戻れ、ホストが消えていればトークンが通じず、ゲームが終わったと分かる

## 根拠

### 表示名では乗っ取れる

選択肢 2 は新しいメッセージが要らないが、**同じ表示名を許している**（[ゲームルール](../spec/game-rules.md)の「参加と退室」）。他人が同じ名前を名乗るだけで、切断中のプレイヤーの席と得点を奪える。

`PlayerId` で名乗らせるのも同じ理由で採らない。id は `room/state` で全員に見えている。トークンは本人にしか送らないので、知っているのは本人だけになる。

### 新規参加扱いでは「再参加」にならない

選択肢 3 は何も足さずに済む。しかし得点を失い、満員なら自分の抜けた枠にも戻れない（切断を退室にしないなら、抜けた枠はまだ埋まっている）。issue の完了条件「切断後に再参加できる」を満たさない。

### プロトコルを2つ増やすことについて

[プロトコル](../spec/p2p-protocol.md)は Player → Host を増やすことに慎重で、プレイヤーに権限を渡すことになるからだった。`rejoin` が渡すのは「自分が誰かを名乗る」ことだけで、状態を変える権限は増えない。結び直すかどうかはホストが決める。

`join/accepted` は、プレイヤーが自分の id を知る手段がそもそも無かったことも埋める。

### 途中経過は既存のメッセージで送る

追いつかせるための専用メッセージ（全状態のスナップショット）は作らない。最初から居た人が受け取ったのと同じ `room/state` → `question/start` → `question/char` を同じ順で並べる。プレイヤー側の処理が1つで済み、公開済みの文字しか送らないので、1文字ずつ公開する意味も崩れない。

`buzz/accepted` の締め切りや、`closed` の後の正解文は送り直さない。`room/state` の `phase` で状態は分かり、それ以上が要るかは UI を作るとき（#24 / #25）に判断する。

### ホストの状態を永続化しない

ホストを復帰させるには、ルーム・出題の状態・得点・トークン表をホストのブラウザに保存し、読み込み直したときに復元する必要がある。復元したホストは全プレイヤーと接続を張り直すことになり、手動シグナリングでは全員分の SDP をもう一度交換する。手間に見合わない。

## 影響

- `shared/protocol` に `join/accepted` / `rejoin` / `unknownToken` と、途中経過を組み立てる `catchUpMessages` を足す
- net の use-case に、ホスト側の `createHostLobby` とプレイヤー側の `createPlayerLobby` を置く。どちらも早押しや回答は扱わない
- `PlayerNetwork` は、呼ぶたびに接続を張り直す `connect()` を持つ
- **トークンはプレイヤーのメモリにだけある。** タブを読み込み直すと失われ、新しく参加することになる
- 回答の権利を持つプレイヤー（`buzzed`）が切れても特別扱いしない。回答の制限時間が過ぎて無回答（誤答）になる

## 再検討のトリガー

- タブの読み込み直しでの離脱が多いと分かった。トークンを `sessionStorage` に残すことを検討する
- SignalR のシグナリング（[ADR 0003](0003-signaling.md)）が揃い、プレイヤーが自分から接続を張り直せるようになった。再招待を待つ必要が無くなる
- 切断中のプレイヤーが枠を埋め続けて困る場面が出た。一定時間で退室扱いにすることを検討する
