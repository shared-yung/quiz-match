# テスト駆動開発（TDD）

**domain / use-case の実装はテストを先に書く。** t_wada（和田卓人）が日本に広めた TDD の進め方に従う。決めた理由は [ADR 0003](../adr/0003-tdd.md)。

テストの置き場所と層ごとの書き分けは [テスト方針](../tooling/testing.md)。この文書は**どの順序で書くか**を扱う。

## 対象

| 対象                              | ルール                                                    |
| --------------------------------- | --------------------------------------------------------- |
| `domain` / `use-case`             | **TDD 必須**                                              |
| `infrastructure` / `presentation` | 任意。スパイクで動きを確かめてからテストを書いてもよい    |
| バグ修正（層を問わない）          | **再現テストを先に書く。** 書けない場合は PR に理由を書く |

外側の層を任意にしているのは、WebRTC や Quasar のように「動くかどうか」をまず確かめたい場面が多いため。ただしバグは、テストが薄い外側の層で起きやすい。だからバグ修正だけは層を問わず再現テストを必須にしている。

再現テストを書こうとして、ロジックが外側の層に漏れていると分かることがある。そのときはロジックを内側の層へ移し、そこでテストする（[オニオンの層構成](../architecture/onion-layers.md)）。

## サイクル

1. **テストリストを書く。** 実現したい振る舞いを箇条書きにする。実装の手順ではなく、外から観察できる振る舞いで書く
2. **Red:** リストから1件選び、失敗するテストを1つ書く。**期待した理由で失敗すること**を確認する（コンパイルエラーや import の失敗は「期待した理由」ではない）
3. **Green:** 最短でテストを通す。きれいさは後回しにする
4. **Refactor:** テストが通ったまま重複を除き、設計を整える
5. 途中で気づいたことは、その場で手を付けずテストリストに足す。2 に戻る

### 歩幅

自信の度合いで歩幅を変える。

- **仮実装:** 期待値をそのまま返して通す。どう実装するか見えないとき
- **三角測量:** 2つ目のテストを足して、仮実装では通らない状態にしてから一般化する
- **明白な実装:** 実装が見えているなら、そのまま書く。Red が想定外の形で続いたら歩幅を戻す

### スパイク

動くか分からないものは、テストを書かずに試作してよい。**試作は捨てる。** 分かったことを元にテストリストを書き、TDD でやり直す。domain / use-case の試作をそのまま残さない。

## 作業の種類ごとの進め方

ブランチの type（[コミット・ブランチ規約](commit-and-branch.md)）ごとに、最初の Red とテストを変えてよいかが変わる。

| 種類                           | 最初の Red                               | テストの変更                                                           |
| ------------------------------ | ---------------------------------------- | ---------------------------------------------------------------------- |
| 新規作成・機能追加（`feat`）   | テストリストの1件目                      | 追加のみ                                                               |
| 仕様変更（`feat`）             | 既存テストを新しい仕様に書き換えて落とす | 実装より**前**に、仕様の変更として書き換える                           |
| バグ修正（`fix`）              | バグを再現して落ちるテスト               | 追加のみ。既存テストを直すなら、既存テストが誤っていた理由を PR に書く |
| リファクタリング（`refactor`） | なし。Green のまま始める                 | **変えない**                                                           |
| テストの無い既存コード         | 今の挙動をそのまま固定する特性テスト     | 追加のみ。固定してから変更に入る                                       |

**テストを変えてよいのは実装の前だけ。** 理由は「仕様が変わった」か「仕様の理解が誤っていた」のどちらか。実装の後でテストを通すために期待値を変えるのは禁止。

リファクタリング中にテストを変えたくなったら、テストが実装の細部に依存しているサイン。リファクタリングを止め、テストを振る舞いの検証に書き直す作業を別に切り出す。

バグ修正では、直したあとに「同じ種類の穴が他にもないか」を考え、見つかったらテストリストに足す。

## issue と PR

- 機能追加・変更の issue には「テストリスト」欄、バグ報告には「再現テスト」欄がある。どちらも任意で、着手前に分かる範囲で書く
- 実装中にテストリストが増減するのは正常。大きく変わったら PR の「計画との差異」に書く
- squash merge でコミットの順序は残らないので、**Red → Green の順序は機械では検査しない。** レビューで、テストが振る舞いを検証しているか（実装をなぞっていないか）を見る

## AI エージェントへのルール

- 実装の前に、テストが**期待した理由で**落ちた出力を示す
- 実装の後でテストや期待値を書き換えない。書き換えが必要だと判断したら、手を止めて理由を述べる
- 1サイクルを小さく保つ。テストリストの複数件をまとめて実装しない
- テストを通すためだけの分岐（テスト環境の判定など）をプロダクションコードに入れない
- スパイクをする場合は、そう宣言してから始め、終わったら捨てて TDD でやり直す
