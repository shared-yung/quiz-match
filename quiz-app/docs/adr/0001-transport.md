# ADR 0001: 通信に WebRTC を採用し、Epic Online Services を見送る

- ステータス: 承認
- 日付: 2026-08-30
- 関連: [#6](https://github.com/shared-yung/quiz-match/issues/6) / [P2P メッセージプロトコル](../spec/p2p-protocol.md)

## 背景

当初の構想は「Epic Online Services (EOS) でマッチングし、ホストプレイヤーを起点にした P2P で通信する」だった。EOS は Fortnite のバックエンドを基盤とした無料のゲームサービスで、ロビー・マッチメイキング・NAT パンチスルーを備えている。

一方このプロジェクトのフロントエンドは **Quasar の SPA**、つまりブラウザで動く。この2つが両立するかを調べた。

## 検討した選択肢

1. **ブラウザ標準の WebRTC DataChannel でホスト星形の P2P**（採用）
2. EOS のネイティブ SDK を使う（Quasar を Electron モードにする）
3. P2P をやめて ASP.NET (SignalR) のサーバ中継にする

## 決定

**選択肢 1 を採用する。EOS は使わない。**

シグナリング（SDP / ICE の交換）は、既にバックエンドとして想定している ASP.NET 側に置く。

## 根拠

### EOS はブラウザから使えない

調査で判明した事実。

- **EOS SDK は C / C# のネイティブ SDK。** 対応プラットフォームは Windows / macOS / コンソール / iOS / Android で、**JavaScript SDK は存在しない**
- **EOS Web API は REST のバックエンドサービスのみ。** 認証・統計・ロビー照会などは扱えるが、**P2P と NAT パンチスルーは含まれない**

つまり SPA では、EOS のマッチングも P2P も動かない。これは設定や工夫で回避できる制約ではない。

### Electron に切り替えてまで使う理由がない

選択肢 2 なら EOS を使える。しかし代償が大きい。

- 共通ルールで定めた **SPA というビルドモードから外れる**
- Node から C の SDK を叩くブリッジ（N-API / koffi）を自作する必要があり、実装コストが大きい
- インストーラの配布が必要になる。**URL を共有するだけで遊べる**という手軽さを失う

早押しクイズに必要なのは低遅延のメッセージ交換であって、EOS が提供するロビー管理やアンチチートではない。得るものに対して失うものが大きすぎる。

### WebRTC で設計意図は維持できる

**「ホストプレイヤーを起点にした P2P」という当初の設計意図は、WebRTC DataChannel のホスト星形トポロジでそのまま実現できる。** ホストが各プレイヤーと個別に `RTCPeerConnection` を張り、ホストが権威を持つ（[P2P メッセージプロトコル](../spec/p2p-protocol.md)）。

EOS が担うはずだった NAT 越えは、WebRTC の ICE / STUN が担う。

### サーバ中継（選択肢 3）を採らない理由

最も単純で、早押しの遅延も実用上は問題にならない。実際シグナリングのために ASP.NET は結局必要になる。

それでも P2P を選ぶのは、**ホスト起点の P2P という当初の設計意図を保てるなら保つべき**だから。中継にすると全メッセージがサーバを経由し、サーバの可用性がゲームの可用性になる。1文字ずつの配信のように頻度の高い通信をサーバに通す必要もない。

ただし**シグナリングだけはサーバが要る**ので、「サーバ不要」にはならない。この点は誤解しないこと。

## 影響

- `net` feature の infrastructure は `RTCPeerConnection` を扱う（#19）
- シグナリングのクライアントが必要になる（#18）。**サーバ側の実装は別リポジトリの作業**
- バックエンドが整うまでは、手動シグナリング（SDP のコピー&ペースト）で先に進められる
- ホストのブラウザが閉じるとゲームが続行できない。ホスト権威の必然的な帰結で、扱いは #20 で決める

## 再検討のトリガー

- **EOS が公式に WebAssembly / JavaScript をサポートする。** 現時点でそうした発表は無い
- デスクトップアプリとして配布する要件が出てくる。その場合は Electron + EOS を選択肢 2 として再評価する
- WebRTC の NAT 越えが実環境で不安定だと判明する。TURN サーバの導入か、サーバ中継（選択肢 3）への切り替えを検討する

3つ目は実測が要る。#19 の実装後、複数のネットワーク環境で接続率を確認して判断する。
