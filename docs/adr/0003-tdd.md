# ADR 0003: domain / use-case の実装は TDD で進める

- ステータス: 承認
- 日付: 2026-10-11
- 関連: [#97](https://github.com/shared-yung/quiz-match/issues/97) / [テスト駆動開発](../workflow/tdd.md)

## 背景

[テスト方針](../tooling/testing.md)は「何をどの層でテストするか」を決めていたが、テストと実装の**順序**は決めていなかった。

順序を決めないと、実装を書いたあとでテストを合わせることになりやすい。そうして書いたテストは実装をなぞるだけで、仕様の誤りを拾えない。AI エージェントに実装させる場合は特にこの傾向が強い。テストが落ちると期待値の側を直して通してしまうこともある。

## 決定

t_wada（和田卓人）が広めた TDD の進め方（テストリスト、Red → Green → Refactor、仮実装・三角測量・明白な実装）を採用する。

- **domain / use-case は TDD 必須**
- infrastructure / presentation は任意。スパイクのあとにテストを書いてもよい
- **バグ修正は層を問わず再現テストを先に書く**
- **テストを変えてよいのは実装の前だけ**
- 機械的には強制しない

## 根拠

### 対象を domain / use-case に絞る

この2層は node 環境で速く回り、fake でテストできる（[テスト方針](../tooling/testing.md)）。短いサイクルを回すのに向いている。ロジックが集まる場所でもあり、カバレッジの閾値もここにだけ課している。

infrastructure（WebRTC、HTTP）と presentation（Quasar のコンポーネント）は、「そもそも動くか」を試作で確かめたい場面が多い。全層で必須にすると形だけの運用になる。

### バグ修正だけは全層で必須にする

バグはテストが薄い場所で起きる。外側の層を任意にした結果、穴はそこに残りやすい。再現テストは、原因を正しく掴めたかの確認と回帰の防止を兼ねる。さらに、ロジックが外側に漏れていることに気づくきっかけにもなる。

### テストを変えてよいのは実装の前だけ

仕様変更では既存テストの書き換えが正当な作業になる。そのため「テストを書き換えてはいけない」という単純な禁止は使えない。区別は**いつ変えたか**でつける。実装の前なら仕様の変更、実装の後なら通すための改ざん。この線は AI エージェントにも人にも同じように説明できる。

### 機械的には強制しない

- squash merge でブランチ上のコミット順が消え、main からは Red → Green の順序を検査できない
- Red のコミットを残す運用にすると、pre-commit やブランチの CI がテストの失敗で落ちる。例外を設けると、本当に壊れたコミットとの区別がつかない

強制はできない。代わりに規約、issue テンプレートの欄（テストリスト / 再現テスト）、レビューで担保する。

## 再検討のトリガー

- テストが実装をなぞるだけになっている、とレビューで繰り返し指摘される
- infrastructure / presentation で、テストのある内側の層では起きないバグが繰り返し起きる（任意にした範囲を見直す）
