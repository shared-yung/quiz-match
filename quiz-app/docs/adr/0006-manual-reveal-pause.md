# ADR 0006: ホストの手動停止は一時停止とし、`revealing` の印で表す

- ステータス: 承認
- 日付: 2026-10-15
- 関連: [#22](https://github.com/shared-yung/quiz-match/issues/22) / [ゲームルール](../spec/game-rules.md) / [P2P メッセージプロトコル](../spec/p2p-protocol.md)

## 背景

ゲームルールの状態表には `revealing` でのホストの操作として「手動停止」があり、プロトコルにも `question/reveal-stop`（`reason: manual`）がある。一方、状態機械には対応するイベントが無く、停止した後にどうなるか（再開できるか、問題が終わるか）が決まっていなかった。#22 でホストの出題操作を作るにあたり決める。

## 検討した選択肢

1. **一時停止にして、再開できる**（採用）
2. 停止したところで読み切りとし、全文公開後と同じ猶予に入る（再開しない）
3. 停止したら問題を打ち切る（`closed` へ。終了理由に「手動」を足す）

一時停止を表す方法についても検討した。

- a. **`revealing` に「停止中」の印（`paused`）を持たせる**（採用）
- b. 新しい状態（`paused`）を足す

## 決定

**選択肢 1 と a を採用する。**

- 停止中は文字送りも猶予のタイマーも止める。再開したら続きの文字から1間隔後に送る
- 停止中も早押しは受け付ける。採用後、誤答（続行）で `revealing` に戻ったら停止を解く
- 全文公開後（猶予中）は停止できない
- プレイヤーには `question/reveal-stop`（`manual`）で知らせる。**再開を知らせる専用のメッセージは作らない。** 次の `question/char` で再開が分かる
- 途中参加・再参加の途中経過は、停止中なら最後に `question/reveal-stop`（`manual`）を足す

## 根拠

### 再開できる停止がいちばん使い道が広い

ホストが止めたくなるのは、問題文の打ち間違いに気づいた、場が騒がしい、といった一時的な事情が多い。打ち切りたいだけなら、選択肢 1 でも止めたまま猶予の代わりにホストが待てばよいが、選択肢 2・3 では読み直しができない。選択肢 3 はプロトコル（`question/end` の理由）も変える。

### 状態を増やすと早押しの経路が倍になる

停止中も押せるので、`paused` を独立した状態にすると `revealing` と同じ遷移（早押し・ロックアウト）を二重に持つことになる。印にすれば、停止の有無で変わるのは「文字を送るか」と「タイマーを張るか」だけで、遷移の大半は共有できる。回線の `phase` も `revealing` のままで済み、プロトコルの `Phase` を変えない。

### 再開のメッセージは要らない

プレイヤーにとって再開とは文字がまた届き始めることで、それは `question/char` が届けば分かる。専用のメッセージを足しても、プレイヤーが知ることは増えず、扱うメッセージの種類と途中経過の組み立てが増えるだけになる。

## 影響

- `QuestionState` の `revealing` に `paused` が増える。再接続時の復元（`questionStateSchema`）もこれを持つ
- `QuestionNotifier` に停止の通知（`revealPaused`）が増える
- プレイヤー側の画面（#24）は、`question/reveal-stop` の理由が `manual` なら「停止中」を表示し、次の `question/char` で解く

## 再検討のトリガー

- 停止中の早押しを止めたい、という要望が出た（印のままでは押下の受け付けを分けられないので、状態を分けるかを見直す）
- 猶予中にも止めたい、という要望が出た
